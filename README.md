# Multi-Agent Orchestration System

A multi-agent AI system using LangChain and LangGraph with intelligent task routing, specialized agent execution, and comprehensive performance monitoring. Supports multiple inference engines (Ollama and llama.cpp).

## WARNING

This system code is generated by an AI code agent and the code it generates is also from an AI LLM. When it comes to code execution there is no-human-in-the-loop.

The primary purpose of this exercise is to learn how to wire and route AI agents. Therefore, no fact checks on responses from the inference and LLM. However, there was one undesirable output but it was an interesting point to note that when the prompt did not ask the LLM not to invent facts nor mocked data was provided, a fictional analysis was made up.

```text
It is autonomous in nature, using a restricted and bounded sandbox is highly recommended for containment and security purposes. Also, run the code with a role with limited and unelevated access.
```

> Note that the model used in this multi-agent example is Qwen2.5-Coder-14B-Instruct (via llama.cpp) or llama2:13b-chat-q4_K_M (via Ollama). For better code quality, use a larger model. This code was tested in CPU-only mode (i.e. no CUDA or TPU was used), it showed the time taken from start to finish was about 5-10 minutes on an Apple M1 silicon with 16GB of RAM. The model alone used about 8GB of RAM.

## 🎯 Core Design Principles

### 1. **Intelligent Routing**
The Router Agent analyzes incoming tasks and dynamically selects the most appropriate specialist:
- **Complexity Assessment**: Evaluates task difficulty (0.0 - 1.0 scale)
- **Domain Matching**: Matches task keywords to agent expertise
- **Confidence Scoring**: Provides confidence level for routing decision
- **Fallback Mechanisms**: Graceful degradation if primary routing fails

### 2. **Specialist Agent Pattern**
Each specialist agent is designed with:
- **Focused Expertise**: Deep knowledge in specific domain
- **Clear Responsibilities**: Well-defined tasks and capabilities
- **Consistent Interface**: Standardized execution and metrics collection
- **Error Isolation**: Failures don't cascade to other agents

### 3. **State Management**
Comprehensive state tracking throughout execution:
- **Message History**: Maintains conversation context
- **Task Metadata**: Tracks task type, complexity, routing decisions
- **Error Tracking**: Captures and logs issues at each step
- **Performance Data**: Collects latency and token metrics
- **Original Result Preservation**: Keeps original outputs before summarization

### 4. **Performance Monitoring**
Built-in metrics collection for optimization:
- **Per-Agent Latency**: Time taken by each agent to execute
- **Token Usage**: Estimated tokens consumed per agent
- **Routing Overhead**: Time spent in routing decision
- **Total Workflow Time**: End-to-end execution time

### 5. **Prompt Engineering**
Each agent uses role-based system prompts to define behavior:
- **System Prompt**: Defines agent role, expertise, and behavior
- **User Message**: Contains the actual task or instruction
- **Assistant Response**: Generated output based on system + user context
- **Conversation History**: Maintains context across multi-turn interactions

### 6. **Pluggable Inference Engines**
Support for multiple LLM backends via factory pattern:
- **Ollama**: Open-source, runs locally, easy to use
- **Llama.cpp**: OpenAI-compatible API, high performance
- **Extensible**: Easy to add new providers (GPT, Claude, etc.)

## 💡 Message Role Architecture

The system uses three core message roles from LangChain:

### 1. **SystemMessage** - Defines Agent Role & Behavior
```python
SystemMessage(content="You are an expert software developer...")
```
- Sets agent's expertise and personality
- Defines behavioral constraints
- Specifies output format expectations
- Injected at the beginning of every agent execution

### 2. **HumanMessage** - User Task/Instruction
```python
HumanMessage(content="Generate a Python function to parse CSV files")
```
- The actual task to be completed
- User's instruction to the agent
- Contains task-specific context

### 3. **AIMessage** - Model Response
```python
AIMessage(content="```python\ndef parse_csv(...):\n...```")
```
- LLM's generated response
- Stored in conversation history
- Used for context in follow-up tasks

### Message Flow Example

```
SystemMessage:   "You are an expert software developer. Focus on..."
HumanMessage:    "Generate a Python function to parse CSV files"
                                    ↓ (LLM Processing)
AIMessage:       "```python\ndef parse_csv(...):\n...```"
                 ↓ (Stored in history for future context)
```

Each agent maintains this proper role hierarchy for consistent, predictable behavior.

## 🤖 Specialist Agents

### Code Generator Agent

**Purpose**: Software development, code generation, debugging, and optimization

**System Prompt Focus**:
- Clean, maintainable code with best practices
- Security and performance considerations
- Detailed explanations of logic
- Code in markdown blocks with language specification

**Capabilities**:
- `code_generation` - Create new code from specifications
- `bug_fixing` - Debug and fix code issues
- `code_review` - Analyze and review existing code
- `performance_optimization` - Improve code efficiency
- `documentation` - Generate code documentation

**Ideal For**:
- "Write a Python function to parse JSON"
- "Debug this database connection issue"
- "Optimize this nested loop algorithm"
- "Generate unit tests for this module"

- Actionable business recommendations

**Capabilities**:
- `data_analysis` - Analyze datasets and patterns

### Router Agent

**Purpose**: Intelligent task analysis and agent selection

**System Prompt Focus**:
- Task classification and complexity assessment
- Domain-to-agent matching
- Confidence scoring based on task-agent fit
- Graceful fallback mechanisms

**Routing Logic**:
- Analyzes task keywords and context
- Computes complexity score (0.0-1.0)
- Selects best-fit agent with confidence
- Provides reasoning for routing decision

## 🔄 Workflow Execution Flow

### Step 1: Task Ingestion
```python
task = "Generate a Python function to analyze CSV files"
state = AgentState(
    task=task,
    task_id="abc123",
    messages=[HumanMessage(content=task)]
)
```

### Step 2: Routing Decision
The Router Agent receives the task and determines:
- Task type and complexity
- Best matching specialist agent
- Confidence and reasoning

**Message Stack at Routing**:
```
SYSTEM:  "You are an intelligent task router..."
USER:    "Generate a Python function to analyze CSV files"
ASSISTANT: 
  AGENT: code_generator
  CONFIDENCE: 0.92
  REASONING: Task requires code generation with data file handling
```

### Step 3: Specialist Execution
Selected agent executes with:
- System prompt injection for domain expertise
- Full message history for context
- User task as the primary instruction
- Response generation with specialized knowledge

**Message Stack at Execution**:
```
SYSTEM:  "You are an expert software developer..."
USER:    "Generate a Python function to analyze CSV files"
ASSISTANT: 
  ```python
  def parse_csv(filepath):
      """Parse CSV file and return data."""
      ...
  ```
```

### Step 4: Summary Generation (Conditional)
Summarizer agent processes the result (skipped for code generator):
- Extracts key findings
- Generates executive summary
- Provides actionable recommendations

**Message Stack at Summarization**:
```
SYSTEM:  "You are an expert executive summarizer..."
USER:    "Summarize this analysis: [previous result]"
ASSISTANT: "Key Points: Identified three critical patterns..."
```

### Step 5: Code Execution (Code Generator Only)
For code generation tasks:
- Extracts Python code from markdown blocks
- Executes in sandboxed environment
- Captures output and errors
- Reports execution status

### Step 6: Output Formatting
Final state includes:
- Agent's response/result
- Executive summary (if applicable)
- Full message history
- Performance report
- Routing information
- Error details (if any)

## 🔧 Inference Engine Setup

### Overview

The system supports multiple inference engines through a pluggable provider architecture:

```
┌──────────────────────┐
│ LLMProviderFactory   │
└──────────────────────┘
           │
    ┌──────┴──────┐
    │             │
    ▼             ▼
┌────────┐  ┌───────────┐
│ Ollama │  │Llama.cpp  │
└────────┘  └───────────┘
```

**Key Benefits**:
- Switch between providers via environment variable
- Same code works with multiple backends
- Easy to add new providers (GPT, Claude, etc.)
- No code changes needed to switch

### Option 1: Ollama (Recommended for Beginners)

Ollama is the easiest to set up - single command to run locally.

#### Installation

**macOS:**
```bash
# Install via Homebrew
brew install ollama

# Or download from https://ollama.ai
```

**Linux:**
```bash
curl -fsSL https://ollama.ai/install.sh | sh
```

**Windows:**
Download from https://ollama.ai/download

#### Pull Model

```bash
# Pull the recommended model
ollama pull llama2:13b-chat-q4_K_M

# Alternative models (smaller/faster):
ollama pull llama3.2:3b
ollama pull mistral:latest
```

#### Start Server

```bash
# Terminal 1: Start Ollama (runs on http://127.0.0.1:11434)
ollama serve
```

#### Configuration

Create `.env` file:

```env
# LLM Provider selection
LLM_PROVIDER=ollama

# Ollama Configuration
MODEL_PATH=http://127.0.0.1:11434
MODEL_NAME=llama2:13b-chat-q4_K_M

LOG_LEVEL=INFO
```

#### Verify Setup

```bash
# Test Ollama connection
curl http://127.0.0.1:11434/api/tags

# Expected: Lists available models
```

### Option 2: Llama.cpp (Advanced - Better Performance)

Llama.cpp provides OpenAI-compatible API with better performance on CPU.

#### Installation

**Prerequisites**: C++ compiler, CMake

**macOS:**
```bash
# Clone and build
git clone https://github.com/ggerganov/llama.cpp.git
cd llama.cpp
make

# Or use Homebrew
brew install llama.cpp
```

**Linux/Windows**: Follow instructions at https://github.com/ggerganov/llama.cpp

#### Download Model

Download quantized GGUF model, e.g.:
```bash
# Example: Qwen 14B
wget https://huggingface.co/Qwen/Qwen2.5-Coder-14B-Instruct-GGUF/resolve/main/Qwen2.5-Coder-14B-Instruct-Q4_K_M.gguf
```

#### Start Server

```bash
# Terminal 1: Start llama.cpp server
./server -m path/to/Qwen2.5-Coder-14B-Instruct-Q4_K_M.gguf -ngl 0 -c 2048

# -ngl 0: Use CPU only (remove for GPU)
# -c 2048: Context size
# Server runs on http://localhost:8080
```

#### Verify Connection

```bash
# Test llama.cpp endpoint
curl http://localhost:8080/v1/chat/completions \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer no-key" \
  -d '{
    "model": "Qwen2.5-Coder-14B-Instruct-Q4_K_M.gguf",
    "messages": [{"role": "user", "content": "Hello"}],
    "temperature": 0.7
  }'

# Expected: JSON response with model's reply
```

#### Configuration

Create `.env` file:

```env
# LLM Provider selection
LLM_PROVIDER=llamacpp

# Llama.cpp Configuration
LLAMACPP_URL=http://localhost:8080
LLAMACPP_MODEL=Qwen2.5-Coder-14B-Instruct-Q4_K_M.gguf

LOG_LEVEL=INFO
```

## 🚀 Usage Example

```python
import asyncio
from multi_agent_system import MultiAgentOrchestrator

async def main():
    # Initialize with default provider (from .env)
    orchestrator = MultiAgentOrchestrator()
    
    # Process task
    task = "Generate a Python function to analyze CSV files"
    result = await orchestrator.process_task(task)
    
    # Print results
    print(f"Selected Agent: {result.selected_agent.value}")
    print(f"Complexity Score: {result.complexity_score:.2f}")
    print(f"Routing Reason: {result.routing_reason}")
    print(f"\nResult:\n{result.result}")
    
    # Execute code if code generator
    if result.selected_agent == AgentType.CODE_GENERATOR:
        exec_result = orchestrator.execute_generated_code(result)
        print(f"\nExecution Status: {exec_result['status']}")
        if exec_result['status'] == 'success':
            print(f"Output:\n{exec_result['output']}")

asyncio.run(main())
```

## 🛡️ Common Issues & Solutions

### Issue: Connection refused on http://127.0.0.1:11434

**Cause**: Ollama server not running

```bash
# Solution: Start Ollama server
ollama serve
```

### Issue: Connection refused on http://localhost:8080

**Cause**: llama.cpp server not running

```bash
# Solution: Start llama.cpp server
./server -m path/to/model.gguf
```

### Issue: Model not found

**For Ollama:**
```bash
# Solution: Pull the model
ollama pull llama2:13b-chat-q4_K_M
```

**For llama.cpp:**
```bash
# Solution: Download model file
wget https://huggingface.co/path/to/model.gguf
```

### Issue: Out of memory errors

```bash
# Solution 1: Use smaller model
ollama pull llama3.2:3b
# Update .env with MODEL_NAME=llama3.2:3b

# Solution 2: For llama.cpp, reduce context size
./server -m model.gguf -c 1024  # Instead of -c 2048
```

### Issue: Slow inference

**Cause**: Model running on CPU only

```bash
# For llama.cpp, enable GPU (if available)
./server -m model.gguf -ngl 33  # offload 33 layers to GPU

# Or just be patient - CPU is slower but will work
```

### Issue: No code blocks found in generated code

**Cause**: LLM didn't format code as expected

```
Check logs for "Result preview" showing what was returned.
The system tries multiple patterns:
1. ```python ... ```
2. ``` ... ```
3. ```python (no newline)
4. ``` (no newline)
5. def statements (fallback)

If none work, the prompt may need adjustment.
```

## 🔐 Security Considerations

- **No Human-in-the-Loop**: Code execution happens automatically
- **Sandboxing**: Run with restricted user account
- **Code Review**: Always review generated code before production use
- **Limited Scope**: Use for development/testing, not production systems
- **Network Isolation**: Keep Ollama/llama.cpp on localhost only
- **Prompt Injection**: System prompts define strict boundaries

## 🚀 Production Deployment

For production use, consider:

1. **Model Selection**: Use larger model (70B) for better quality
2. **Hardware**: GPU acceleration (CUDA/Metal) for faster inference
3. **Scaling**: Deploy on dedicated server with load balancing
4. **Monitoring**: Implement logging and metrics collection
5. **Code Review**: Add human validation before code execution
6. **Sandboxing**: Use containers (Docker) for execution isolation
7. **Provider Redundancy**: Support multiple backends as fallback
